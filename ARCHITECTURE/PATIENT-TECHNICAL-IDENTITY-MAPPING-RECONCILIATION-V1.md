DOCUMENT = PATIENT TECHNICAL IDENTITY MAPPING RECONCILIATION
STATUS = RECONCILIATION DECISION
SCOPE = PATIENT PERSISTENCE IDENTITY ONLY

## 1. PURPOSE

This reconciliation resolves the historical persistence-level deferral of the
technical Patient identifier representation against the later closed PostgreSQL
physical authority.

No Product, Domain, CPN, Case, Visit, Clinic Day, Actor, Authentication,
Authorization, API, UI, repository behavior, or unrelated persistence decision
is reopened or redesigned by this reconciliation.

## 2. AUTHORITATIVE CHRONOLOGY

The technical Patient persistence identity was resolved through the following
bounded PostgreSQL authority sequence:

1. PostgreSQL schema implementation definition established the bounded physical
   implementation boundary.
2. PostgreSQL physical naming authority established `patient_id` as the
   authorized physical column representing the technical Patient persistence
   identifier.
3. PostgreSQL physical data-type authority subsequently closed the previously
   deferred physical representation as PostgreSQL `UUID` generated by
   PostgreSQL 18 native `uuidv7()`.
4. PostgreSQL schema implementation definition and implementation plan were
   reconciled to that closed physical authority.
5. Commit `0fb028c` implemented the authorized physical representation in
   `backend/persistence/schema.sql`.

This chronology supersedes only the earlier unresolved persistence-level
technical representation deferral. It does not rewrite the historical
documents that recorded the state before this authority was closed.

## 3. PATIENT TECHNICAL IDENTITY MAPPING

The canonical Patient persistence mapping is:

- Physical column = `patient_id`
- Technical persistence identity = `patient_id`
- Physical type = PostgreSQL `UUID`
- Physical generation = PostgreSQL 18 native `uuidv7()`
- Product-level stable reference = `clinic_patient_number`
- CPN remains distinct from `patient_id`
- CPN remains the stable Product-level clinic reference
- `patient_id` is not a second Product Patient identity
- `clinic_patient_number` is not the technical persistence primary key
- CPN is not a Visit identifier

## 4. DOMAIN BOUNDARY PRESERVED

The Patient domain does not own the PostgreSQL technical identifier
representation.

Therefore:

`domain/PATIENT-DOMAIN-BOUNDARY.md`
`TECHNICAL_PERSISTENCE_KEY = DEFERRED`

remains valid as a Domain boundary statement.

The PostgreSQL UUID materialization is a persistence-layer authority and must
not be copied into the Patient domain merely to reconcile this document.

## 5. PRODUCT IDENTITY PRESERVED

The following Product-level Patient identity rules remain unchanged:

- Patient identity remains stable.
- CPN remains stable once established.
- A returning Patient resolves to the existing Patient identity and CPN.
- A Visit does not create a new Patient.
- A Visit does not create a new CPN.
- CPN is not a replacement for the technical persistence identity.

## 6. HISTORICAL DEFERRED STATEMENTS

Earlier Persistence Technical Contract, Persistence Schema Definition,
Persistence Implementation Plan, and PDR-B01 material contain statements that
the technical identifier type/representation or UUID-vs-numeric choice was
deferred.

Those statements are preserved as historical authority state.

Where those documents govern the current Patient persistence implementation,
the later closed PostgreSQL physical authority is the current technical
materialization authority:

`patient_id = PostgreSQL UUID generated by PostgreSQL 18 uuidv7()`

No unrelated UUID-vs-numeric decision is resolved by this reconciliation.

In particular, Actor and Authentication UUID-vs-numeric decisions remain
outside this Patient persistence reconciliation unless separately authorized.

## 7. API BOUNDARY

Existing API references to:

`/patients/{patientId}`

remain structurally valid.

This reconciliation does not authorize API implementation, request/response
schema changes, authentication, authorization, or exposure of persistence
details.

The exact application/API mapping of `patientId` to the technical Patient
identity remains a separately bounded implementation concern.

## 8. REPOSITORY BOUNDARY

This reconciliation does not implement or authorize additional Repository
behavior.

It establishes only the identity mapping that an authorized Patient
Repository may later use:

`technical Patient identity -> patient_id UUID`

Repository implementation remains governed by the existing Persistence Access
Mechanism and Persistence Implementation Authorization authorities.

## 9. CPN BOUNDARY

CPN generation remains PostgreSQL-authoritative through the established
PostgreSQL sequence mechanism.

The CPN and technical Patient identity must remain separate:

`patient_id != clinic_patient_number`

No CPN redesign is introduced.
